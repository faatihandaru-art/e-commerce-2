MASALAH YANG HARUS DISELESAIKAN
====================================================================

SAAT INI kolom stok (`stock`) tersimpan LANGSUNG di tabel
product_variants (ditambahkan lewat migration terpisah belakangan,
add_stock_to_product_variants_table). Ini TIDAK SESUAI dengan
dokumen arsitektur bagian 6.3, yang merancang stok sebagai entitas
TERPISAH per VARIAN dan per GUDANG, lewat tabel inventories yang
merujuk ke warehouses. Desain saat ini tidak bisa merepresentasikan
"variant A punya 50 unit di gudang Jakarta dan 20 unit di gudang
Bali" -- cuma bisa satu angka stok per varian secara keseluruhan.

Selain itu, fitur "stock" saat ini SALAH TEMPAT secara UX -- muncul
di form Tambah/Edit Produk (halaman Catalog), padahal secara konsep
bisnis, stok adalah tanggung jawab modul INVENTORY yang terpisah
(lihat dokumen arsitektur bagian 4.2: Catalog dan Inventory adalah
dua modul admin yang berbeda, dengan role staf yang bisa berbeda
juga -- Catalog Manager vs Inventory Manager).

====================================================================
STRUKTUR DATABASE YANG WAJIB DIIKUTI
====================================================================

Sesuai dokumen arsitektur bagian 6.3:

TABEL warehouses
id              bigint unsigned, primary key
name            varchar(150), nama gudang (misal "Gudang Jakarta")
code            varchar(50), unique, kode singkat (misal "JKT-01")
address         text, nullable
status          enum('active','inactive'), default 'active'
created_at, updated_at

TABEL inventories
id                  bigint unsigned, primary key
warehouse_id        bigint unsigned, foreign key ke warehouses,
                    cascade on delete
variant_id          bigint unsigned, foreign key ke product_variants,
                    cascade on delete (SESUAIKAN nama kolom foreign
                    key ke product_variants -- cek dulu apakah kolom
                    di tabel lain yang sudah ada, seperti cart_items,
                    memakai nama variant_id, IKUTI KONVENSI YANG
                    SUDAH ADA supaya konsisten)
quantity_on_hand    int unsigned, default 0, stok fisik total
quantity_reserved   int unsigned, default 0, stok yang sedang
                    ditahan untuk pesanan pending (untuk SEKARANG
                    di tahap ini, field ini disediakan strukturnya
                    tapi BELUM diisi logic otomatis -- fitur
                    reservasi stok saat checkout adalah pekerjaan
                    terpisah nanti sesuai roadmap Fase 4, JANGAN
                    membangun logic reservasi otomatis sekarang)
reorder_level       int unsigned, default 0, ambang batas stok
                    menipis (untuk indikator "stok menipis" di
                    dashboard)
created_at, updated_at

UNIQUE COMPOSITE: (warehouse_id, variant_id) -- satu varian hanya
boleh punya SATU baris inventory per gudang, sesuai dokumen
arsitektur bagian 6.8.

TUGAS KAMU
====================================================================

LANGKAH 1 -- KONFIRMASI STRUKTUR YANG SUDAH ADA
Sebelum menulis migration, jalankan di tinker:
   php artisan tinker
   >>> Schema::getColumnListing('product_variants')
   >>> \App\Models\ProductVariant::count()
   >>> \App\Models\ProductVariant::whereNotNull('stock')->where('stock', '>', 0)->get(['id', 'sku', 'stock'])
CATAT hasil query terakhir -- ini daftar varian yang PUNYA stok
sekarang, yang HARUS dipindahkan datanya, jangan sampai ada yang
terlewat.

LANGKAH 2 -- MIGRATION warehouses DAN inventories
Buat migration untuk kedua tabel sesuai struktur di atas. Jalankan
php artisan migrate.

LANGKAH 3 -- SEEDER GUDANG DEFAULT
Buat database/seeders/WarehouseSeeder.php yang membuat MINIMAL satu
gudang default (misal name: "Gudang Utama", code: "MAIN") -- karena
toko ini sepertinya baru operasi dengan satu lokasi untuk sekarang,
tapi struktur tabel tetap mendukung multi-gudang untuk masa depan
sesuai dokumen arsitektur. Daftarkan di DatabaseSeeder.php, jalankan
php artisan db:seed --class=WarehouseSeeder.

LANGKAH 4 -- MIGRASI DATA STOK YANG SUDAH ADA (PALING PENTING,
JANGAN SAMPAI DATA HILANG)
Buat migration KHUSUS untuk migrasi data (bukan cuma ubah struktur),
atau buat Artisan command sekali-jalan, yang:
- Ambil gudang default dari Langkah 3
- Untuk SETIAP baris di product_variants yang punya nilai stock
  (dari hasil query Langkah 1), buat SATU baris baru di inventories
  dengan warehouse_id = gudang default, variant_id = id varian itu,
  quantity_on_hand = nilai stock yang lama, reorder_level = boleh
  default masuk akal seperti 5
- SETELAH migrasi ini dijalankan, VERIFIKASI dengan query:
  >>> \App\Models\Inventory::sum('quantity_on_hand')
  Bandingkan totalnya dengan jumlah total dari
  ProductVariant::sum('stock') di Langkah 1 -- HARUS SAMA PERSIS.
  Jika tidak sama, JANGAN lanjut, laporkan masalahnya dulu.

LANGKAH 5 -- MODEL
Buat app/Models/Warehouse.php: $fillable name, code, address,
status. Relasi hasMany(Inventory::class).

Buat app/Models/Inventory.php: $fillable warehouse_id, variant_id,
quantity_on_hand, quantity_reserved, reorder_level. Relasi
belongsTo(Warehouse::class), belongsTo(ProductVariant::class,
'variant_id'). Tambahkan accessor availableQuantity() yang
mengembalikan quantity_on_hand - quantity_reserved (sesuai bagian
8.2 dokumen arsitektur, walau logic reservasi penuh belum dibangun
di tahap ini, accessor ini tetap berguna untuk ditampilkan).

Update app/Models/ProductVariant.php: tambahkan relasi
hasMany(Inventory::class, 'variant_id'), dan method helper
totalStock(): int yang menjumlahkan quantity_on_hand dari SEMUA
baris inventory milik varian ini (dipakai untuk menampilkan total
stok gabungan semua gudang di halaman produk, TANPA perlu tahu
detail per gudang).

LANGKAH 6 -- ACTION (app/Domain/Inventory/Actions/ -- buat folder
Domain/Inventory baru, sejajar dengan Domain/Catalog yang sudah ada)
- AdjustStockAction.php: terima Inventory (atau kombinasi
  warehouse_id+variant_id), jumlah penyesuaian (bisa positif untuk
  nambah stok masuk, negatif untuk stok keluar/rusak/hilang), dan
  alasan (string, misal "Stok masuk dari supplier", "Koreksi hasil
  stock opname", "Barang rusak"). Method ini HARUS:
  * Memakai DB::transaction() dan lockForUpdate() pada baris
    inventory yang diubah (sesuai prinsip concurrency di dokumen
    arsitektur bagian 8.2, walau konteksnya beda -- prinsip locking
    saat mengubah angka stok tetap penting untuk mencegah race
    condition kalau dua admin menyesuaikan stok yang sama
    bersamaan)
  * Validasi: quantity_on_hand hasil akhir TIDAK BOLEH negatif
  * Simpan LOG penyesuaian ini (lihat Langkah 7 soal tabel
    inventory_movements yang perlu dibuat sebagai bagian dari
    melengkapi tabel yang hilang)

LANGKAH 7 -- MELENGKAPI TABEL YANG HILANG DARI DOKUMEN ARSITEKTUR
Selain warehouses dan inventories yang sudah dibuat di atas, cek
kembali dokumen arsitektur bagian 6 dan database yang sudah ada
sekarang -- BUAT MIGRATION untuk tabel-tabel berikut yang BELUM ada
(cek dulu satu per satu dengan Schema::hasTable() di tinker sebelum
membuat, supaya tidak duplikat jika ternyata sudah ada):

   a. inventory_movements (bagian 6.3) -- PALING PRIORITAS karena
      dibutuhkan Langkah 6 di atas untuk audit trail:
      id, warehouse_id (FK), variant_id (FK), type (enum:
      'in','out','adjustment'), quantity (int, boleh negatif untuk
      merepresentasikan pengurangan), before_quantity (int),
      after_quantity (int), reference (varchar nullable, untuk
      catatan asal perubahan), reason (varchar nullable),
      created_by (FK ke users, nullable), created_at

   b. stock_reservations (bagian 6.3) -- struktur saja untuk
      sekarang (belum dipakai logic-nya, disiapkan untuk Fase 4
      nanti): id, order_id (nullable dulu karena order belum
      terhubung), warehouse_id (FK), variant_id (FK), quantity,
      status (enum: 'active','released','committed'), expires_at,
      created_at

   c. warehouses dan inventories -- SUDAH dibuat di Langkah 2, skip

   d. Cek juga tabel-tabel dari kategori LAIN yang menurut riwayat
      project ini kemungkinan besar juga belum ada -- JALANKAN
      Schema::hasTable() untuk cek satu per satu, dan BUAT migration
      untuk yang BELUM ADA dari daftar berikut (struktur ikuti
      dokumen arsitektur bagian 6.6 dan 6.7):
      - payment_transactions (charge/refund/void history per payment)
      - webhook_logs (idempotency provider callback, unique
        composite provider+event_id)
      - shipments, shipment_items
      - refunds, refund_items
      - returns, return_items
      - promotions, promotion_rules, promotion_actions (jika belum,
        cek dulu apakah coupons yang sudah ada dianggap cukup untuk
        tahap ini -- jika ragu, BUAT strukturnya tapi TANDAI di
        dokumentasi bahwa fitur promosi lanjutan ini belum
        diimplementasikan logicnya)
      - wishlists, wishlist_items
      - settings (key-value config toko)
      - pages (CMS sederhana)
      - audit_logs (SUDAH ADA berdasarkan pengecekan sebelumnya,
        skip jika terkonfirmasi ada)
      - exports (riwayat export laporan)
      - customer_notes

   JANGAN terburu-buru membuat SEMUA sekaligus tanpa berpikir --
   PRIORITASKAN inventory_movements dan stock_reservations dulu
   (dibutuhkan fitur Inventory ini), lalu SISANYA boleh dibuat
   sebagai migration kosong/struktur dasar tanpa Model/Controller
   lengkap (itu pekerjaan fase berikutnya sesuai roadmap 8 fase),
   CUKUP pastikan strukturnya TERDAFTAR di migration supaya database
   rekan tim dan production nanti bisa disetup lengkap dari nol.

LANGKAH 8 -- CONTROLLER (app/Http/Controllers/Admin/)
   InventoryController.php:
   - index(): Inertia::render('Admin/Inventory/Index') dengan props

     reorder_level)

     AdjustStockAction $action): terima jumlah penyesuaian dan

   WarehouseController.php (CRUD sederhana, TIDAK perlu serumit

LANGKAH 9 -- ROUTE (di dalam grup middleware(['auth','staff'])
->prefix('admin') yang sudah ada)
